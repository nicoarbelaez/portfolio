## Architecture

The Android app uses Expo Router for navigation and Supabase as the full backend: Auth, PostgreSQL, Realtime, Storage and Deno Edge Functions. Media is stored in Cloudinary. The project rule: simple operations go straight from the client, multi-step logic goes through an Edge Function.

## Key decisions

1. **Edge Functions for multi-step logic.** Posting with media or validating evidence touches storage, the database and several rules. One function runs them together and the client makes a single call. Simple reads and writes go straight to Supabase.
2. **Security in the database.** RLS on the tables and audit triggers. The rules do not depend on the client behaving.
3. **Evidence approval with triggers.** Approve and reject logic lives in SQL and has a test suite (`supabase/tests`, files 001 to 009).
4. **Cloudinary for media.** Post photos and videos are uploaded to Cloudinary from the `create-post` Edge Function, through a shared helper in `_shared/cloudinary.ts`.
5. **Automated releases.** Conventional commits, Husky with lint-staged and semantic-release produce versions with no manual steps.
6. **Refactor by domain.** On `develop` the code moves from flat folders to `features/` per domain (communities, competitions, feed, notifications, profile). The migration is in progress.

## Testing, CI and deployment

There is no JavaScript test framework. The database has SQL tests (`supabase/tests`) and the Edge Functions have Deno tests for `cloudinary` and `response`. GitHub Actions runs two workflows: a check on every PR (lint, dependencies with Expo Doctor and an Android build check) and a production release on push to `main`. EAS profiles build an APK for preview and production. The latest published release is v1.2.0, with an `.aab` asset.
