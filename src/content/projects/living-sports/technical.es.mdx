## Arquitectura

La app Android usa Expo Router para la navegación y Supabase como backend completo: Auth, PostgreSQL, Realtime, Storage y funciones Edge en Deno. Los medios se almacenan en Cloudinary. La regla del proyecto: operaciones simples desde el cliente, y lógica de varios pasos en una función Edge.

## Decisiones clave

1. **Funciones Edge para lógica de varios pasos.** Publicar con medios o validar una evidencia toca el storage, la base y varias reglas. Una función las ejecuta juntas y el cliente hace una sola llamada. Las lecturas y escrituras simples van directo a Supabase.
2. **Seguridad en la base.** RLS en las tablas y triggers de auditoría. Las reglas no dependen de que el cliente se comporte.
3. **Aprobación de evidencias con triggers.** La lógica de aprobar o rechazar vive en SQL y tiene una suite de pruebas (`supabase/tests`, archivos 001 a 009).
4. **Cloudinary para medios.** Las fotos y los videos de las publicaciones se suben a Cloudinary desde la función Edge `create-post`, con un helper compartido en `_shared/cloudinary.ts`.
5. **Release automatizado.** Commits convencionales, Husky con lint-staged y semantic-release generan las versiones sin pasos manuales.
6. **Refactor por dominios.** En `develop` el código pasa de carpetas planas a `features/` por dominio (comunidades, competencias, feed, notificaciones, perfil). La migración está en curso.

## Pruebas, CI y despliegue

No hay framework de pruebas de JavaScript. La base tiene pruebas SQL (`supabase/tests`) y las funciones Edge tienen pruebas en Deno para `cloudinary` y `response`. GitHub Actions corre dos flujos: una revisión en cada PR (lint, dependencias con Expo Doctor y verificación de build Android) y un release de producción al hacer push a `main`. Los perfiles de EAS generan un APK para pruebas y producción. La última versión publicada es la v1.2.0, con un `.aab`.
